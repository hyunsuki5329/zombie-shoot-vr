# VR 좀비 FPS 완수용 Goal 프롬프트

작성 기준: 2026-09-20 · 개발 문서 1.1 · Unity 6000.3.23f1 / XRI 3.5.1

이 파일은 실행 지침이다. 사용자가 이 파일을 지정하여 `/goal`을 실행하는 시점부터 아래의 개발·Git 작업을 수행한다. 프롬프트를 작성하거나 읽어 달라는 요청만으로 개발이나 원격 저장소 작업을 시작하지 않는다.

## 1. 목표와 역할

너는 이 프로젝트의 Unity PC VR 개발 책임자다. 현재 워크스페이스와 승인된 개발 문서를 바탕으로, **실제로 촬영한 방·강의실 두 맵에서 K2 양손 사격과 왼손 수동 재장전으로 좀비의 무한 웨이브를 플레이하는 학기 제출용 게임**을 완성하라.

구현, 테스트, 실제 기기 검증 준비와 결과 반영, 성능 개선, Git 관리, 실행 빌드, 재현 가능한 소스, 출처, 보고서·발표·시연 자료까지 책임진다. 계획 제안이나 코드 작성만으로 목표를 완료하지 않는다. 아래 종료 기준이 충족될 때까지 검증 가능한 작업 단위로 계속 진행한다.

사용자의 최신 결정, 적용되는 상위 지침과 도구 권한을 따른다. 사용자에게 필요한 결정은 일찍 묻되, 이미 승인된 설계와 통상적인 개발·검증·Git 절차를 매번 다시 승인받지 않는다. 사용자가 정한 사용량·시간 한도와 중단 요청을 준수한다.

## 2. 먼저 확인할 프로젝트와 기준 문서

- 워크스페이스: `D:/Unity Project/Zombie Shoot VR`
- Unity 프로젝트: `D:/Unity Project/Zombie Shoot VR/Zombie Shoot VR`
- 현재 개발 문서: 워크스페이스의 `docs/vr-fps-project-docs/`
- 진입 문서: `docs/README.md`, `docs/vr-fps-project-docs/README.md`
- 읽을 순서: `02-requirements.md` → `03-architecture.md` → `04-implementation-plan.md` → `08-test-plan.md` → 나머지 문서와 `config/balance.initial.json`

기능은 02, 인터페이스와 상태는 03, 순서는 04, 수치는 06과 JSON, 시험과 완료 판정은 08, 제출은 09를 기준으로 삼는다. 결정과 근거는 10에 남긴다. 문서의 코드 조각과 수치는 실제 코드·실측 결과인지 구분하고 설치된 패키지 API에 맞게 구현한다.

`AGENTS.md` 및 참조된 `.github/agents/main_instruction.prompt.md`, `part_agent.prompt.md`, `work_agent.prompt.md`가 있으면 읽고 적용한다. 사용자 지침의 역할 매핑을 유지한다. 파일이 없으면 없다고 기록하고 내용을 만들어 내지 않는다. 문서 간 실질적인 충돌은 영향이 있는 지점에서 해결하며, 관련 없는 작업까지 멈추지 않는다.

`docs/shared-chat-2026-09-18/`는 이전 대화·자료의 원본 보관본이다. 현재 개발 기준과 혼동하거나 원본을 덮어쓰지 않는다. XRI 3.3.2 후보를 현재 설치 버전인 3.5.1로 되돌리지 않는다.

시작 시 실제 파일로 Unity 6000.3.23f1, VR 템플릿 10.0.0, XRI 3.5.1, URP 17.3.0, OpenXR 1.17.1, Input System 1.20.0의 상태를 재확인한다. AI Navigation과 Test Framework는 설치 상태를 확인하고 필요한 부분만 구성한다. 실제 프로젝트 경로를 유지하며 새 Unity 프로젝트로 임의 교체하지 않는다. 버전 변경이 꼭 필요하면 호환성 근거와 영향부터 제시한다.

## 3. 반드시 유지할 게임 규칙

1. Windows PC VR, Quest Pro와 Virtual Desktop을 사용한다. 방과 강의실은 사전에 제작한 두 맵이며 집에서도 선택한다. 실제 플레이 장소와 맵의 위치 정합은 요구하지 않는다.
2. 총은 K2 한 종류이며 오른손에 영구 부착한다. 왼손으로 앞부분을 잡은 상태에서만 오른손 트리거로 자동 사격한다. 왼손을 놓으면 즉시 사격을 차단한다.
3. 재장전은 왼손으로 앞부분 해제 → 탄창 탈거 → 버리기 → 허리에서 새 탄창 꺼내기 → 삽입 → 앞부분 다시 잡기 순서다. 새 탄창 30발, 무한 예비 탄창, 잔탄 교체 허용, 제거한 잔탄 폐기, 버린 탄창 재사용 금지다. 장전 손잡이 단계와 자동 재장전 연출로 대체하지 않는다.
4. 왼쪽 스틱 연속 이동, 오른쪽 스틱 연속 회전이다. 머리 보기·숙이기·기울이기를 유지하며 카메라 강제 반동을 넣지 않는다.
5. 근접·원거리 좀비를 구현한다. 원거리 공격은 예고가 있고 눈에 보이는 피할 수 있는 투사체다. 벽은 총탄·투사체·근접 피해를 막으며 적은 가구를 돌아 이동한다.
6. 웨이브는 무한히 이어지되 각 웨이브의 적 할당량과 동시 생존 수는 제한한다. 생성 대기와 생존 적이 모두 0일 때만 한 번 클리어한다. 생성 실패를 가짜 처치나 정상 생성으로 계산하지 않는다.
7. 최대 HP 100, 초기 클리어 회복 20, 피격 보호 0.5초, 웨이브 사이 준비 8초다. 클리어와 사망이 겹치면 사망이 우선한다. 초기 밸런스 조정은 문서의 허용 범위와 실제 시험을 따른다.
8. 최고 기록은 실제로 시작한 최대 웨이브다. 5를 클리어하고 6에서 사망하면 wave 6이며 준비 중에는 다음 번호를 기록하지 않는다. 맵별로 같은 도전의 웨이브와 처치 수를 함께 저장하고 동률이면 처치 수로 비교한다.
9. 오른팔 전완 UI에 HP·현재 웨이브·처치 수를 표시한다. 총구·재장전·표적을 가리지 않아야 하며 실제 팔꿈치 추적은 요구하지 않는다.
10. 일시정지 중 전투·가상 이동·관련 물리·타이머를 멈추고 머리·컨트롤러 추적은 유지한다. 재개 시 실제 왼손 잡기와 탄창 상태를 다시 평가한다.
11. 적·투사체·버린 탄창·사체·효과의 객체 수를 제한한다. 두 맵에서 공통 전투 코드를 사용한다.
12. 무료 에셋의 실제 사용 조건과 재배포 조건을 기록한다. 멀티플레이, 추가 총기, 계정, 온라인 랭킹, 임의 공간 자동 업로드는 이번 범위에 추가하지 않는다.

## 4. 실행 방식과 작업 분해

기존 설계와 구현 계획을 이번 실행의 승인된 기준으로 사용한다. 적용되는 실행·검증 스킬을 따라 현재 작업에서 직접 구현하며, 실질적인 요구사항 변경 없이 전체 기획 승인 절차를 반복하지 않는다. 추가 에이전트나 별도 작업 생성은 사용자의 요청 또는 적용 지침의 명시적 허용이 있을 때만 사용한다.

P01~P12를 의존 순서대로 수행한다. 한 작업이 크면 `P04-a`, `P04-b`처럼 독립적으로 설명·검증·리뷰할 수 있는 단위로 나눈다. 파일 하나마다 PR을 만들거나 프로젝트 전체를 하나의 거대한 PR로 묶지 않는다.

| 단계 | 완성할 결과 |
|---|---|
| P01 | 현재 Unity 환경, XR 입력, 시험장, Windows 빌드와 기기 연결 |
| P02 | 작은 실제 스캔의 스케일·양안 가림·충돌·성능 검증과 GS/메시 선택 |
| P03 | 연속 이동·회전, 머리 움직임과 충돌 |
| P04 | 오른손 고정 K2, 양손 사격과 벽 관통 차단 |
| P05 | 왼손 수동 재장전과 탄창 수명·소유권 |
| P06 | 근접·원거리 좀비, 경로·공격·처치 |
| P07 | 웨이브·HP·정지·사망·재도전 규칙 |
| P08 | 오른팔 UI, 메뉴, 맵별 영구 기록 |
| P09 | 실제 방·강의실 맵과 공통 전투 통합 |
| P10 | 첫 조작 안내, 소리·진동·전투 피드백 |
| P11 | 객체 풀, 성능, 장시간 안정성 |
| P12 | 최종 빌드·소스·재현 안내·출처·보고서·발표·시연 |

각 단위는 **완료 조건 정의 → 구현과 필요한 테스트 → 실행 검증 → 변경 검토 → 커밋 → push → PR → 리뷰 반영 → 병합 → 진행 기록 갱신** 순서로 마무리한다. 해당 단위의 필수 시험이 통과하지 않았으면 완료라고 표시하지 않는다. 아직 필요한 검증을 명시한 초안 PR은 가능하다.

## 5. Git 저장소와 첫 실행

이 프롬프트 실행에 한하여, 프로젝트 범위의 로컬 Git 초기화, 작업 브랜치 생성, 커밋, 지정 저장소로 push, PR 생성·갱신, 해당 PR의 검토 결과·답변 작성, 조건을 충족한 PR 병합을 승인한다. 이 범위의 통상적인 Git 작업은 반복 확인 없이 진행한다. 공개 게시·비용 지출·권한 확대는 이 승인에 포함하지 않는다.

먼저 Git 루트, 변경 파일, 현재 브랜치, worktree 여부, remotes, 인증 상태, 원격 기본 브랜치와 보호 규칙을 확인한다. 이 파일 작성 시점에는 워크스페이스와 Unity 하위 폴더 모두 Git 저장소가 아니었으므로 실행 시 다시 확인한다.

저장소가 없다면 **워크스페이스 루트**에 하나를 초기화하여 `docs/`와 기존 Unity 하위 프로젝트를 함께 관리한다. Unity 프로젝트를 이동하거나 중첩 저장소를 만들지 않는다. 원격이 없고 사용자가 대상을 지정하지 않았다면 저장소 소유자와 이름 또는 URL만 한 번 요청한다. 요청한 대상이 확정되면 기존 저장소를 연결하거나, 새 저장소 생성 요청이라면 비공개로 생성한다. 계정·대상을 추측하지 않는다. 인증이나 대상 결정을 기다리는 동안 가능한 로컬 작업과 커밋을 진행한다. Git 작성자 이름·이메일도 기존 설정을 우선하며 임의로 신원을 만들지 않는다.

첫 커밋 전에 실제 파일 목록과 크기를 확인하고 Unity에 맞는 `.gitignore`를 만든다. 중첩 Unity 경로에도 적용되게 한다.

- 포함: 프로젝트 코드·씬·프리팹·필요한 `.meta`, `Packages/manifest.json`, `Packages/packages-lock.json`, `ProjectSettings`, 현재 개발 문서, 재현 스크립트, 허용된 에셋과 출처.
- 제외: `Library`, `Temp`, `Obj`, `Logs`, `UserSettings`, 자동 생성 IDE 파일, 빌드 캐시·실행 파일, 자격 증명·라이선스 키.
- 원본 보관본 `docs/shared-chat-2026-09-18/`와 강의 PDF/PPT, 사적인 방·강의실 촬영 원본은 로컬에 보존하고 기본 Git 추적 대상에서 제외한다.
- 가공한 스캔과 외부 에셋도 공유 범위·라이선스를 확인한다. 큰 바이너리를 올려야 하면 첫 추적 전에 Git LFS 지원과 용량을 확인하고 필요한 유형에만 적용한다. 업로드가 허용되지 않는 자원은 별도 로컬 제출물과 확보·복원 안내로 관리하여 재현 경로를 남긴다.

ignore 설정만 믿지 말고 실제 staged diff와 파일 목록을 확인한다. 무관한 사용자 변경을 섞지 않고 작업 파일을 지정하여 stage한다. 최초 기준선 커밋은 새 저장소의 기본 브랜치를 만드는 데 필요한 예외로 허용하며, 이후 개발은 작업 브랜치와 PR을 사용한다.

## 6. 작업 단위별 커밋·push·PR·병합

1. 원격이 연결되어 있으면 변경을 fetch하고 기준 브랜치와 사용자 작업 상태를 확인한다. 새 단위는 최신 통합 상태에서 `codex/p04-two-hand-fire`처럼 목적이 드러나는 브랜치로 시작한다. 기존 브랜치·PR이 있으면 이어 사용한다.
2. 변경의 이유와 범위를 먼저 정한다. 사용자 파일이나 씬 설정을 광범위하게 덮어쓰지 않는다. 격리가 필요한 경우에만 worktree를 사용하고 같은 Unity 프로젝트를 여러 에디터가 동시에 수정하지 않게 한다.
3. 필요한 시험·컴파일을 실행한 후 diff, `.meta`, 자원 참조, package lock, 의도하지 않은 씬 변경을 검토한다. 수정이 필요하면 고치고 영향받은 검증을 다시 실행한다.
4. 완료한 단위마다 최소 한 번 커밋한다. 메시지는 `feat(P04): 양손 잡기 조건에서만 K2 사격 허용`처럼 유형·작업 ID·결과를 포함한다. 검증 전 보존이 꼭 필요하면 WIP임을 명시하고 완료 커밋과 구분한다.
5. 작업 브랜치를 지정 원격에 push하고 PR을 생성하거나 갱신한다. 성공한 PR은 현재 Codex 작업에 첨부한다. PR에는 해결한 문제, 변경 결과, 연결 R/P/T 번호, 실제 실행한 검증, 미실행 항목, 기기 확인 절차를 간결하게 적는다.
6. PR diff를 요구사항과 회귀 위험 관점에서 다시 검토한다. CI·허용된 리뷰 도구·실제 리뷰 의견을 확인하고 타당한 지적은 재현·수정·검증한 뒤 추가 커밋과 push로 반영한다. 반영하지 않은 의견에는 기술적 이유를 기록한다. 자체 검토와 다른 사람의 승인을 구분한다.
7. 해당 단위의 필수 검증, 최신 변경에 대한 검토, 저장소의 필수 CI와 승인 조건이 충족되고 해결되지 않은 중대한 결함이 없으면 병합한다. 저장소 정책을 우선하고 별도 정책이 없으면 squash merge를 기본으로 한다. 실제 기기 시험이 완료 조건인 단위는 그 시험 전까지 초안 또는 대기 상태로 둔다. 별도 단위로 검증된 기반 코드만 먼저 병합할 수 있으며 전체 P 단계 완료로 확대하지 않는다.
8. 병합 SHA와 원격 반영을 확인하고 로컬 통합 브랜치를 안전하게 동기화한 뒤 다음 작업으로 넘어간다. 공유 변경이나 승인 상태를 버리는 강제 push, 보호 규칙 우회, `reset --hard`, 사용자 변경 삭제를 하지 않는다. 충돌은 의미를 확인하여 해결하고 검증한다.

CI가 없으면 현재 사용 가능한 Unity 라이선스·실행 환경·비용 범위에서 재현 가능한 검증 방법을 구성한다. CI 실행 불가나 건너뜀을 통과로 표시하지 않는다. 필수 외부 승인을 자체 승인으로 대체하거나 대답 없는 리뷰를 승인으로 간주하지 않는다. 병합 조건을 임의로 낮추지 않는다.

push·인증·CI·리뷰 대기 때문에 막히면 로컬 커밋과 증빙을 보존하고 남은 원격 작업을 기록한다. 가능한 독립 작업은 계속하며 의미 없이 같은 실패나 대기 상태를 반복 조회하지 않는다. 타인의 열린 PR은 현재 프로젝트에 필요한 것으로 범위를 확인한 뒤 검토하고, 사용자 승인 범위를 벗어나는 PR을 임의 병합하지 않는다.

## 7. 촬영·실기 검증 등 사람에게 필요한 입력

처음부터 필요한 자료를 구체적으로 안내한다: 원격 저장소 대상, 최신 수업 공지의 제출일·파일 형식·외부 스캔 앱 조건, 작은 공간의 스캔 결과와 기준 길이 두 개, Quest Pro·Virtual Desktop 연결 및 검증 가능 여부. 이미 제공된 답은 다시 묻지 않는다. 예전 문서의 마감일과 작업시간 추정치를 현재 확정 사항으로 취급하지 않는다.

촬영은 05의 가이드를 따른다. 작은 구역의 Scaniverse Classic 앱 내 연속 스캔과 내보내기를 먼저 확인한다. 별도 복원용 원본은 겹치는 사진을 우선하고 일반 영상은 프레임 추출 경로로 사용한다. 일반 카메라 영상과 앱 내 스캔을 혼동하거나 가져오기 기능을 확인 없이 가정하지 않는다. 아이폰 기본 모델에 LiDAR를 요구하지 않는다.

GS는 실제 Quest Pro의 양안 표시·깊이 가림·스케일·성능 시험을 통과해야 채택한다. 충돌체가 시각적 깊이 가림까지 자동 해결한다고 가정하지 않는다. 기존 P02의 제한된 검증 시간을 적용하고, 실패 시 계획된 텍스처 메시 대안을 시험한다. 촬영본이 없으면 InteractionLab과 임시 도형으로 전투·입력·규칙·테스트를 진행하되 최종 실제 공간 구현으로 표시하지 않는다.

기기를 직접 착용해야 하는 단계에서는 바로 실행할 수 있는 빌드, 시험 ID, 조작 순서, 기대 결과, 반환받을 기록 형식을 먼저 준비한다. 사용자의 실제 관찰·로그·측정 결과를 받아 반영한다. 기기 테스트나 자료를 기다리는 동안 수행 가능한 독립 작업을 계속한다. 실행하지 않은 시험, 촬영, 승인, 성능 수치를 만들어 내지 않는다.

## 8. 검증 기준과 증빙

- 순수 규칙은 필요한 EditMode 시험으로 발사 조건·탄창·웨이브·사망 우선·맵별 기록의 경계 조건을 검증한다. 중요한 기능·버그 수정은 재현 가능한 실패를 확인한 뒤 구현·수정하고 통과를 확인한다.
- PlayMode에서는 Unity 객체·씬·충돌·이벤트·재시작·풀 수명을 검증한다. 단순 문구·문서·가역적인 Inspector 변경에는 구현을 그대로 복제하는 시험을 억지로 만들지 않는다.
- 실제 설치된 Unity 경로로 컴파일, 필요한 시험, Windows 빌드를 실행한다. 도구 실행 성공과 게임 검증 통과를 구분하고 결과 XML·로그·빌드 산출물을 확인한다. 에디터 잠금이나 라이선스 문제가 있으면 기존 작업을 강제 종료하지 말고 해결에 필요한 정보를 제시한다.
- XR 조작, 두 눈 표시와 가림, 오른팔 UI, 재장전 손동작은 실제 Quest Pro에서 확인한다. 편집기의 평면 화면이나 테스트 더블을 실제 기기 증빙으로 사용하지 않는다.
- 초기 성능 기준은 고정된 Virtual Desktop 설정의 72Hz, CPU·GPU 각각 p95 12.5ms 이하이다. 두 시간을 합산하지 않는다. p99·끊김·메모리·객체 상한도 기록한다. 각 맵 30분, 재도전과 맵 전환 각각 10회 등 08의 시나리오를 수행한다.
- R01~R20을 T01~T20과 연결한다. 시험 결과에는 날짜·빌드/소스 식별자·환경·맵·절차·기대·실제·판정·증빙을 남긴다. 최종 버전에 영향을 주는 변경 후에는 해당 결과를 다시 검증한다.

## 9. 진행 기록과 재개

워크스페이스의 `docs/progress.md`를 진행 현황의 진입점으로 만들고 유지한다. 기존 구현·시험 기록이 있으면 연결하여 중복 문서를 늘리지 않는다. 최소한 다음을 기록한다.

- 현재 단계와 작업 단위, 완료 조건, 다음 실행 항목.
- 구현 완료 / 자동 검증 완료 / 실제 기기 검증 대기 / 실패 / 외부 입력 대기를 구분한 상태.
- 단위별 관련 R/P/T 번호, 커밋 SHA, PR URL, 병합 상태와 증빙 경로.
- 미해결 결함, 필요한 사용자 입력, 의사결정과 근거 문서 링크.
- 마지막 검증의 기준 커밋과 재실행 명령·조건.

실제 결과와 증빙을 커밋에 포함하고, 생성 후 알게 된 SHA·PR URL은 이어지는 문서 갱신이나 PR 기록으로 연결한다. 문서에 자기 자신의 최종 커밋 SHA를 넣기 위해 커밋을 끝없이 다시 만들지 않는다.

재개 시 진행 기록과 실제 Git·파일·PR 상태를 대조하고 미완료 지점부터 이어 간다. 완료 작업을 반복하거나 추측한 진행률을 보고하지 않는다. 사용자에게는 현재 성과, 검증 결과, 다음 작업, 꼭 필요한 입력을 짧게 알린다.

현재 목표 기능의 상태 규칙을 따른다. 실제 종료 조건을 모두 충족한 경우에만 complete로 표시한다. pause는 사용자가 요청했을 때만 사용한다. 사용자·외부 입력 없이는 더 진행할 수 없는 경우에는 제공된 도구의 blocked 조건을 충족한 뒤 해당 상태로 보고하고, 재개에 필요한 구체적인 한 가지 행동을 남긴다. 사용량 한도·권한·중단 지시를 우회하는 반복 실행이나 별도 자동화를 만들지 않는다.

## 10. 최종 종료 조건

다음 조건이 모두 충족되어야 프로젝트 완수로 판정한다.

1. P01~P12의 필수 결과물이 있고 R01~R20에 실제 시험 결과가 연결되어 있다. 필수 시험에 미실행·실패가 남아 있지 않다.
2. 실제 방과 강의실 두 맵에서 Quest Pro로 선택 → 이동 → 양손 사격 → 왼손 재장전 → 웨이브 → 사망 → 기록 → 재도전 흐름이 동작한다.
3. 성능·장시간 시험을 통과하고 S0·S1 결함이 없다. 남은 S2는 영향과 재현 조건을 공개한다. 완료를 위해 요구사항이나 통과 기준을 조용히 낮추지 않는다.
4. 최종 Windows 실행 빌드, 필요한 자원을 포함한 소스와 복원 안내, 에셋 출처, 테스트·성능 결과, 실행 안내, 실제 결과에 근거한 보고서·발표자료·시연 영상이 준비되어 있다. 최신 과제 형식과 일치한다. LMS 업로드나 외부 제출은 별도 사용자 지시를 따른다.
5. Git에 포함하기로 한 최종 소스·문서가 지정 원격의 통합 브랜치에 반영되어 있고 관련 PR·필수 검토가 정리되어 있다. Git에서 제외한 자원도 허용된 제출물 또는 복원 경로로 확보되어 있다. 사용자의 무관한 로컬 변경은 보존한다.
6. 최종 전달에는 실행 빌드 경로, 소스 커밋/빌드 식별자, 저장소와 주요 PR 링크, 검증 결과, 알려진 한계, 실행·시연 방법을 제공한다.

이제 실제 상태를 확인하고, 최소한의 진행 기록과 Git 추적 범위를 준비한 뒤 **P01의 첫 검증 가능한 작업부터 실행하라.** 이미 실행을 마친 부분이 있다면 확인된 다음 미완료 단위부터 이어 가라.
