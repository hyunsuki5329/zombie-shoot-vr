## 1. 판단과 권장 방향

**Method A를 권장한다.** 실제 방의 치수와 장애물 배치를 기준으로 게임용 환경을 만들고, 사진 질감 대신 테마 모델·재질을 사용한다. 현재 스캔의 찢어진 가구와 누락 벽을 그대로 최종 외형으로 사용하는 부담을 줄이고, 공간 데이터·충돌·외형을 분리하는 개발 기여도 설명하기 좋다.

다만 스캔을 버리고 임의의 방을 만드는 방식이 되어서는 안 된다. 실측 → 수동 구조 해석 → 구조 데이터 → 충돌/경로 → 테마 외형의 대응을 증빙한다. 자동 사물 인식, 스캔 복원 알고리즘 자체 개발, 실제 방과의 물리적 위치 정합을 구현했다고 주장하지 않는다. 사용자는 집에서 스틱으로 가상 맵을 이동하며, 현실 가구와 가상 가구가 안전하게 정합된다는 보장은 없다.

현재 목표의 ‘촬영 공간 외형을 보여주는 방식’을 ‘촬영 공간의 구조를 재현하는 방식’으로 바꾸는 **명시적인 설계 변경**이다. 2026-10-12 사용자 결정에 따라 요구사항·P02/P09 인수 기준·보고서·Goal 프롬프트를 함께 갱신했다. 제공된 수업 공지에는 사진 질감이나 특정 복원 기법 사용 의무가 없지만, 이것만으로 교수자의 평가나 최종 승인을 보장하지 않는다.

개발 순서는 내 방 구조 분리 → 내 방 폐가 외형 → 실제 강의실 구조 확보 → 강의실 폐교 외형이다. Room에는 AbandonedHouse, Classroom에는 AbandonedSchool을 고정한다. 두 색상의 Cube만 만들면 시제품이며 완성된 월드가 아니다. 같은 방에 학교 외형을 입혀 강의실 맵으로 대신하지 않는다. 지원 대상은 이 두 공간으로 한정한다.

## 4. 데이터와 생성기 경계

```text
로컬 Room.fbx / 별도 Classroom 스캔 + 각 공간의 실측 + 수동 확인
    → 맵별 RoomStructureDefinition (서로 독립된 구조 자산)
        → 구조 생성기: CollisionRoot / 시작점 / 생성점 / NavMesh
        → 테마 생성기 + EnvironmentThemeProfile: VisualRoot/ThemeGenerated

별도 편집용 참조 씬: 원본 스캔과 생성 결과 비교
최종 Room 씬: 폐가 외형 + 내 방 구조
최종 Classroom 씬: 폐교 외형 + 실제 강의실 구조
두 최종 씬 모두 원본 스캔 참조 없음
```

`MapRoot.visualRoot`, `collisionRoot`, `playerSpawn`, `enemySpawns` 계약을 유지한다. `StructureRoot`는 필요할 때만 편집용 앵커로 추가한다. 데이터 자산과 Hierarchy 양쪽에 같은 수치를 따로 편집하게 만들지 않는다. 구조 데이터가 원천이고 나머지는 생성 결과다.

테마 생성은 구조·충돌·NavMesh를 **읽기만** 한다. 구조를 수정한 경우에만 구조 생성·NavMesh 재베이크·경로 재검증을 별도 작업으로 수행한다. 테마 변경 자체가 물리 판정을 바꾸면 실패다.

### RoomStructureDefinition 권장 필드

아래는 데이터 계약 제안이며 바로 붙여 넣는 완성 C# 코드는 아니다.

| 필드 | 의미 |
|---|---|
| schemaVersion, structureId, mapId | 형식 버전·구조 식별·기존 맵 연결 |
| measuredRoomSize | 실내4.3×2.45×3.5m. 전체 복도를 포함하는 bounds와 구분 |
| elements | 고유 ID를 가진 구조 요소 목록 |
| playerSpawn, enemySpawns | 루트 로컬 위치와 필요한 회전. 기존 값을 정확히 이전 |
| sourceProvenance | 실측/스캔 추정/게임용 추가 구분, 확인 상태. 원본 직접 Unity 참조는 넣지 않음 |
| navigationSettings | 재베이크에 필요한 agent 설정·voxel·수집 레이어/대상 식별 |

런타임 구조 자산에 개인 원본의 절대 경로를 저장하지 않는다. 원본 해시·보정 이력과 파일 위치 안내는 별도의 로컬 출처 기록으로 관리한다. 추상화한 방 구조도 개인정보가 될 수 있으므로 자동 공개 대상으로 취급하지 않는다.

### StructureElement 권장 필드

- `id`: 안정적이고 중복 없는 식별자.
- `type`: Floor, Ceiling, Wall, DoorOpening, Bed, Desk, Chair, Wardrobe, Obstacle부터 시작한다. 아직 쓰지 않는 타입을 모두 구현할 필요는 없다.
- `localCenter`, `localRotation`, `size`: **MapRoot 로컬 좌표, 미터, 박스 중심 기준, 크기는 회전 전 로컬 축 길이**. MapRoot 스케일은1을 요구하거나 비단위 스케일을 명시적으로 처리한다.
- `origin`: Measured / ScanEstimated / GameExtension 및 확인 상태. 벽 두께·높이 등 추정값을 실측처럼 표시하지 않는다.
- `collisionRole`: None / Solid. v1 Solid는 기존 WorldSolid 이동·사격·투사체 차단 규칙을 그대로 따른다.
- `navigationRole`: Excluded / WalkableSurface / BlockingGeometry. 바닥과 복도 바닥은 보행 표면, 가구 상단은 보행 영역이 되지 않게 한다. ‘NavMesh에 기여’ bool 하나로 이 차이를 표현하지 않는다.
- `visualKey`: 테마 매핑용 키. 구조 ID와 테마별 에셋 이름을 결합하지 않는다.

`DoorOpening`은 문짝 박스가 아니다. 기존 양쪽 벽과 상부 보를 별도 요소로 유지하고 통로 내부에는 충돌·불투명 외형을 생성하지 않는다. 새 닫히는 문 기능은 이번 범위 밖이다.

현재 `ScannedRoomSetup.Calibrate`의 원본 축 변환/오프셋/스케일을 이미 적용한 값을 구조 데이터로 이전한다. 테마 생성기에서 다시 보정하지 않는다. 강의실은 별도 실측과 보정값을 사용하며 내 방 수치를 복제하지 않는다.

## 5. 테마와 프리팹 계약

EnvironmentThemeProfile은 테마 ID, 구조 타입/visualKey별 Material·Prefab·fit 규칙·fallback을 가진다. Room의 고정 테마는 AbandonedHouse, Classroom의 고정 테마는 AbandonedSchool이다. 두 씬은 각자의 실제 공간 구조를 사용한다. 런타임 테마 선택 메뉴는 요구하지 않으며 편집기에서 생성해 저장하는 방식부터 구현한다.

벽·바닥·천장은 URP 재질과 단순 메시를 사용한다. UV 반복은 미터 기준으로 정의해 벽 길이가 달라져도 질감 밀도가 일정하도록 한다. 필요 시 면별 UV 또는 검증된 타일링 방식을 사용한다. 조명·그림자·후처리는 별도 비용이므로 PBR을 쓰면 자동으로 더 빠르거나 더 자연스럽다고 보장하지 않는다.

가구 프리팹에는 다음 메타데이터를 둔다.

- 모델 기준 크기, 기준 피벗/바닥 접점, 앞 방향, 배치 회전 보정.
- 기준 bounds는 프리팹 로컬 공간에서 계산한다. 회전된 world AABB로 scale을 반복 계산하지 않는다.
- 구조 요소별 허용되는 fit 방식과 시각/충돌 오차. v1은 solid proxy에 잘 맞는 모델을 우선한다.

**Stretch는 벽·기본 도형에 적합하다.** 의자·가구의 무조건 XYZ 늘리기는 피한다. **UniformFit이 시각적으로 작은 가구를 만들면서 큰 보이지 않는 충돌체를 남기면 채택하지 않는다.** 맞는 모델·명시적 solid 기반 외형·다른 프리팹으로 해결하고, 테마 생성기가 충돌을 몰래 바꾸지 않는다.

특히 기존 Desk는 통째로 막힌 박스다. 다리만 있는 책상을 넣으면 빈 하부에서 총알이 막히는 문제가 생긴다. 하부가 막힌 캐비닛형 책상 등 기존 판정을 설명하는 외형을 사용하거나, 구조 변경을 별도 승인·검증 작업으로 분리한다. Wardrobe→작은 사물함 등 크기가 크게 달라지는 대응에도 같은 규칙을 적용한다.

외부 프리팹의 Collider·Rigidbody·NavMeshAgent·NavMeshObstacle·Modifier·게임 스크립트·불필요한 카메라/조명/오디오는 자동 수용하지 않는다. 허용된 시각 컴포넌트만 사용하는 준비된 프리팹을 검증한다. `VisualRoot`는 WorldSolid가 아니어야 하며, 포함된 하위 오브젝트도 점검한다. MeshCollider만 제외하는 것으로 끝내지 않는다.

외부 에셋을 임의 취득하지 않는다. v1은 직접 만든 placeholder로 파이프라인을 검증하고, 최종 시각 품질 단계에서 사용자가 확보한 허용 에셋의 출처·사용·제출 범위를 기록한다. Placeholder 생성과 미술 완성은 별도 상태다.

## 6. 안전한 편집기 생성

1. 대상 씬·MapRoot·구조·테마 참조를 검증한다. 미저장 사용자 변경을 자동 폐기하지 않는다.
2. ID 중복, NaN/Infinity, 양수가 아닌 크기, 무효 회전, 필수 매핑 누락을 교체 전에 실패 처리한다.
3. 임시 생성 루트에서 결과를 구성한다. prefab bounds/피벗/허용 컴포넌트를 검증한다.
4. 충돌·문 통로·바닥 높이·생성점과 외형의 대응을 검증한다.
5. 성공했을 때 생성기 소유 표식이 있는 `VisualRoot/ThemeGenerated`만 교체한다. 이름만으로 사용자 오브젝트를 삭제하지 않는다.
6. 실패 시 임시 결과만 정리하고 기존 정상 외형을 보존한다. 편집기 실행은 Undo 그룹과 명시적 저장 정책을 제공한다. 배치 실행은 격리 프로젝트에서 성공한 경우에만 저장한다.
7. 같은 입력 반복 실행 시 결과 수·재질·변환이 같아야 한다. 불필요한 재질 복제와 GUID 재생성을 피한다. 입력이 같으면 재생성을 건너뛰는 방식도 가능하다.

현재 ScannedRoomSetup은 새 씬을 만드는 배치 전용 도구다. 이를 열려 있는 Unity 씬에 그대로 실행하지 않는다. 전체 맵 생성과 테마 외형 갱신을 별도 진입점으로 분리한다.

## 7. 스캔 참조와 최종 빌드

이 절의 제외 대상은 Method A 구조 참조 메시/촬영 원본이다. P13용 가공 GS는 별도 현실 관찰 씬의 명시적 예외다. 테마 씬의 NavMesh·충돌·생성기에 GS 의존성을 추가하지 않는다.

`Renderer.enabled=false` 또는 GameObject 비활성은 화면을 숨기는 조치일 뿐, 최종 빌드에서 스캔 메시·재질·텍스처가 제외됐다는 증명이 아니다.

권장 v1은 **빌드 목록에 없는 별도 로컬 참조 씬**에 원본 스캔을 두는 방식이다. 편집기에서 테마 씬과 비교하되 참조 씬을 최종 씬에 저장하거나 구조/테마 자산에서 직접 연결하지 않는다. EditorOnly 분리를 선택한다면 그 처리 결과도 실제 빌드 의존성으로 검증한다.

- 기존 사진형 Room 씬/로컬 백업은 비교·복구용으로 보존한다.
- 전환 중에는 별도 테마 미리보기 씬에서 검증하고, 통과한 뒤 기존 Room 경로와 메뉴를 연결한다.
- 원본 스캔 없이도 구조+허용 테마 자산만으로 최종 테마 맵을 생성·빌드할 수 있어야 한다.
- 최종 빌드 씬·Resources/Addressables 등 포함 경로·빌드 보고서에서 원본 스캔 의존성이 없는지 확인한다. 단순 실행 화면만으로 판단하지 않는다.
- 현재 NavMesh는 Git 제외 `External/RoomScan/Generated`에 있다. 구조 데이터만으로 재생성할 새 경로·복원 절차를 정하고 저장된 씬의 GUID 참조도 갱신한다. 원본 FBX 의존성을 끊었다고 하면서 NavMesh 복원을 그 폴더에 계속 의존시키지 않는다.

### 자동 시험에서 놓치지 않을 것

- 기존 `MeasuredRoomHasTextureSeparateCollisionAndReachableAnchors`는 최종 씬에4096 텍스처·10만 이상 삼각형의 스캔을 요구한다. 이를 그대로 유지하면 Method A와 충돌한다. 로컬 참조 스캔 검사와 최종 테마 구조 검사를 분리한다. 최종 테마는 원본 없는 환경에서도 시험 가능해야 한다.
- 바닥4.3×3.5m, 벽/침대/천장 Raycast, 중앙 생성, 복도 연결, 바닥 생성 커버리지, 정지·기록·재도전·10회 재로딩 등 게임 회귀 기준은 유지한다.
- 테마 전후 콜라이더의 transform/size/layer/enabled/trigger/탐색 modifier를 비교한다. 객체 개수만 비교하지 않는다.
- 각 맵의 외형 재생성 시 저장된 NavMesh 참조·설정 불변과 주요 경로/도달성을 검사한다. 재베이크를 한 경우 바이너리 해시만으로 의미상 동일성을 판정하지 않는다.
- 프리팹 피벗이 중심이 아닌 경우,90도 회전,중첩 scale,매핑 누락,하위 Collider/Obstacle,중복 ID,예외 발생 시 정상 씬 보존을 검사한다.
- 빈 문 통로가 외형으로 막히지 않고, 닿는 바닥/가구가 보이는 위치와 맞는지 확인한다. 일반적인 모델 AABB 일치만으로 탄환 판정 정확성을 입증하지 않는다.
- 원본 스캔 없는 복사본에서 생성·시험·빌드를 실행하고 의존성 결과를 남긴다.

### 실제 VR 인수

실제 스케일·벽 밀착·가구 접촉·보스/크롤러 통로·생성 예고·탄환/투사체 엄폐·양안 가림·어두운 곳의 적/HUD 가독성을 확인한다. 기존 목표인72Hz에서 CPU/GPU 각각 p95 12.5ms 이하와맵별 약5분 플레이 시험은 새 테마의 실제 측정으로 판정한다. 그림자와 재질 복잡도가 늘어 성능이 악화될 수도 있다. ‘가벼운 모델로 바꿨다’는 설명으로 측정을 대체하지 않는다.

## 9. 완료의 두 수준

**파이프라인 시제품 완료:** 구조 데이터 분리, 맵별 고정 프로필 연결 및 placeholder 생성, 게임 구조 불변, 안전한 생성, 스캔 없는 생성 경로, 자동 회귀 통과. 이 상태는 최종 환경 미술 완성이 아니다.

**Method A 맵 인수 완료:** 최종 사용 외형과 충돌의 대응, 출입구·복도·어두운 구역 가독성, 실제 VR 동작·성능, 외부 자산 출처·복원·빌드 증빙까지 완료. 프로젝트 전체 종료는 별도 실제 강의실과 최종 제출물 등 기존 Goal 조건도 충족해야 한다.

## 10. 구현 재개 시 사용할 수정 프롬프트

아래는 사용자가 **별도로 구현을 지시할 때** 사용할 프롬프트다. 검토 문서 자체는 실행 권한이 아니다.

```text
기존 VR FPS 프로젝트에 Method A를 구현하라. 이 문서의 현재 기준과 단계/시험을 실행 기준으로 사용하고, 기존 Goal의 나머지 필수 기능은 유지한다.

원본 Room.fbx는 로컬 구조 참조용으로 보존하고, 수동 검증한 구조 데이터에서 게임용 테마 외형을 생성한다. 자동 semantic segmentation은 구현하지 않는다. 현재 approximate4.3x3.5m 실내, 추정2.45m 높이, 게임용2.2x2.8m 복도/1.4m 출입구, player spawn,7enemy anchors, Room minSpawnDistance1.5m 및1.5초 예고를 보존한다.

먼저 기존 코드를 읽고 현재 충돌/앵커/NavMesh 기준선과 테스트 결과를 기록하라. RoomStructureDefinition에 로컬 미터 좌표·회전·중심 기준 크기·의미·출처·충돌/탐색 역할을 명시하라. MapRoot의 현재 계약을 유지하고 구조 생성기와 테마 생성기를 분리하라.

내 방에 AbandonedHouse를 먼저 구현하고, 별도 실측·스캔한 강의실에 AbandonedSchool을 구현하라. 두 맵의 테마는 고정하며 같은 Room의 외형 교체로 강의실을 대신하지 마라. 편집기 생성만 우선하고 런타임 테마 메뉴는 추가하지 않는다. 외부 에셋은 임의 취득하지 않으며 placeholder 파이프라인과 최종 미술 완료를 구분하라. Prefab 피벗/방향/크기와 시각/충돌 일치를 검증하고 UniformFit으로 보이지 않는 큰 충돌체를 남기지 마라.

테마는 VisualRoot/ThemeGenerated만 소유한다. Collider/Rigidbody/탐색/전투 컴포넌트가 섞이지 않게 검증하라. 임시 생성 후 성공 시 교체하고 실패 시 기존 외형과 사용자 오브젝트를 보존하라. 테마 변경은 CollisionRoot,spawns,NavMesh를 수정하지 않는다. 현재 배치 전용 전체 씬 생성기를 열린 사용자 씬에 실행하지 않는다.

스캔은 별도 로컬 편집용 참조로 분리하고 최종 빌드 씬/런타임 자산에 원본 참조를 남기지 마라. Renderer 끄기만으로 빌드 제외를 주장하지 않는다. NavMesh도 구조 데이터만으로 복원할 수 있도록 경로/참조/안내를 정리하라.

스캔 외형을 강제하던 테스트는 참조 검사와 테마 검사로 분리하되, 기존 벽/가구 Raycast·중앙 생성·복도/바닥 도달성·전투·정지·기록·재도전 회귀는 유지하라. 반복 생성/잘못된 데이터/피벗·회전/숨은 게임 컴포넌트/실패 복구 및 원본 없는 생성·빌드를 검증하라.

작업 단위마다 검증 후 커밋·push·PR·리뷰를 수행하라. 사용자 변경을 보존하고 현재 원격 기준을 확인하라. VR 인수 전에는 해당 PR을 대기로 유지한다. 자동 시험으로 양안/편안함/성능을 통과 처리하지 마라. 두 테마를 두 실제 맵으로 계산하거나 전체 프로젝트 완료로 확대하지 마라.

자동 사물 인식,영상 업로드,서버 복원,생성형3D,파괴 효과,공간 재배치,실시간 현실 정합은 범위 밖이다. 새 요구사항과 충돌하면 결정 근거를 기록하고 기존 요구를 조용히 낮추지 마라.
```

## 11. 프로젝트 설명에 사용할 표현

> 실제 공간을 스캔·실측하고 구조를 수동으로 데이터화한 뒤, 내 방은 폐가, 실제 강의실은 폐교 외형으로 재구성하는 VR FPS를 제작한다. 스캔 복원은 외부 도구를 활용하고, 구조 데이터·테마 생성·충돌/경로 통합·VR 전투 및 검증을 직접 구성한다.

지원 범위는 제작자의 내 방과 실제 강의실 두 맵으로 한정한다.
